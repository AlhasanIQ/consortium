Reasoning Workflow Architecture

How Consortium's reasoning workflows are structured, why they're designed this way, and the principles behind each choice.

Four-Layer Structure

Reasoning workflows use a layered architecture that separates reusable aggregation, user-facing reasoning, composition, and benchmark-specific concerns. Each layer builds on the one below it:

L3WRAPPERS
Benchmark wrappers — benchmark-
Thin harness: calls an L1 child and adds benchmark-specific output contract (MCQA & non-MCQA variants). e.g. benchmark-informed-captain-synthesis
L2COMPOSITES
Composites — composite-
Orchestrate multiple L1 primitives. e.g. composite-judge-synthesis-cheap
L1PRODUCT
Primitives — reasoning-
General-purpose reasoning strategies. Benchmark-agnostic, usable by any caller. This is the product — powers the Round Table UI, the API, and routing. e.g. reasoning-judge-pick
L0INTERNALS
Aggregation workflows — aggregation-
Reusable aggregation internals: collection, extraction, judging, scoring, synthesis, peer review, selection. Builder/admin only; not shown in Ensemble. e.g. aggregation-synthesis, aggregation-majority-vote, aggregation-peer-matrix
Why four layers? L0 aggregation workflows make method internals reusable and inspectable without turning them into user-facing products. The L1 primitives are the product. Benchmark wrappers are a testing concern only. Mixing benchmark-specific instructions (like "answer with a single letter") into the primitives would degrade them for general use — the wrapper layer keeps that separation clean.

How wrappers wire up

MCQA L3 wrappers reduce the L1 output to a single option label:

input→ child_workflow (L1)→ contract_extract→ result (collect)

Non-MCQA wrappers (e.g. benchmark-math-*-cheap) are thinner — grading parses/evaluates expressions in the benchmark harness:

input→ child_workflow (L1)→ result (collect)
Rule: Benchmarks must evaluate L1 workflows, not L0 aggregation workflows directly. L0 is implementation structure; L1 is the benchmarkable product behavior.

Design Principles

1

Blind Evaluation

Aggregators that show responses to an LLM anonymize agent identities. Judge/scoring relabel responses with letters (A, B, C…); debate_decide instead groups answers into neutrally-named camps (CampAlpha…) kept distinct from option letters. Real IDs are remapped after the LLM responds.

Why: LLMs favor familiar model names — a judge may prefer a response labeled "GPT-4" over an identical "Unknown Model". Anonymization eliminates this confound.

2

Model Diversity Over Sampling

Each workflow uses agents from different architectures (Gemini, Mimo, Grok) rather than one model many times at high temperature.

Why (Condorcet): Ensemble accuracy improves when voters make independent errors. Duplicate models have perfectly correlated errors. Diversity is the primary source of variation, so temperature stays low.

3

Evaluator Independence

Evaluators should ideally differ from all answering agents. Full independence is a goal; tuned assignments may reuse a strong evaluator on cost/quality tradeoffs.

Why: If the same model answers and judges, it's biased toward its own reasoning patterns. An independent evaluator assesses content on its merits.

4

Dynamic Task-Specific Rubrics

Scoring & peer-matrix support rubric_mode: "dynamic" — an LLM generates a task-appropriate rubric from the question alone, before seeing answers.

Why: A static rubric can't discriminate across task types. Adds one LLM call per aggregation (~15–25% cost), but aggregation is the cheapest part of the pipeline.

Exception (Principle 2): reasoning-self-consistency-majority-pick intentionally uses a single model 3× at elevated temperature to capture sampling diversity — a valid, cheaper alternative when testing one strong model's consistency.

Workflow Builder representation: Aggregation can be authored as a visible aggregation node between answer producers and a presentation result node. The L0 seed JSON is a descriptor and Fork template, not the execution source of truth; the backend compiler owns the compiled DAG used by execution and Expand. Evaluator role by method: Cognitive demand varies. judge reasons through competing argument chains. scoring assesses each response against criteria. synthesis understands, integrates, and generates new text. debate_decide judges answer camps while fallback nodes preserve deterministic consensus selection. peer_matrix distributes evaluation across models. Benchmark contract_extract nodes only regex-extract a letter — no LLM reasoning in the common case. Optimal settings are determined empirically through benchloop.

Workflow Primitives

Each L1 primitive captures a distinct reasoning strategy — a specific hypothesis about how multiple models (or samples) produce better answers than one. Together they cover the strategy space without redundancy: each exists because it tests something no other primitive tests. The tuning invariants mark what must be preserved so a primitive doesn't silently collapse into a different one.

Every L1 primitive composes an L1 answer layer with an L0 aggregation method. The normal total LLM calls on each card below = L1 agent calls + top-level L0 aggregation calls; Builder preview also shows conditional branches such as repair prompts.

reasoning-majority-pick 3 calls total

3 agentsL1 calls+0 aggregationL0 calls=3 total(tie → synthesis, +1)
L0 USED majority_vote method · workflow aggregation-majority-vote
3 agents (independent)→ extract answers→ count / majority_vote

Multiple models answer independently; answers are extracted and counted — no LLM evaluates anything. If each model is independently more likely right than wrong, the majority is more reliable than any individual (Condorcet).

What makes it unique: Zero-cost aggregation. The baseline — isolates whether multi-model diversity alone improves accuracy, without any evaluation intelligence.

Tuning invariant: Aggregation must stay purely mechanical (extraction + counting). Adding LLM reasoning would make this a more expensive judge.

reasoning-self-consistency-majority-pick 3 calls total

3 samplesL1 calls · 1 model ×3+0 aggregationL0 calls=3 total(tie → synthesis, +1)
L0 USED majority_vote method · workflow aggregation-majority-vote
1 model × 3 samples (high temp)→ extract answers→ majority_vote

One model answers the same question three times at higher temperature, producing different reasoning paths. Reaching the same answer through different routes means high confidence.

What makes it unique: The only single-model primitive. Tests whether one model's internal variance suffices — different reasoning paths from the same weights — rather than multiple architectures.

Tuning invariant: Must use a single model. Temperature high enough for genuinely different paths. Multiple models makes this vote; too-low temperature makes all samples identical.

reasoning-judge-pick 4 normal · 5 preview

3 agentsL1 calls+1 top-level aggregationL0 call=4 normal(+1 repair in preview)
L0 USED judge method · workflow aggregation-judge
3 agents (independent)→ judge selects winner

Multiple models answer independently. One independent evaluator reads all responses and picks the best, assessing the full reasoning chain — not just the final answer. The unanimous fallback can select the agreed output, but the judge job remains visible and scheduled.

What makes it unique: Cheapest LLM-based evaluation. A single evaluator catches logical errors, unjustified leaps, and self-contradictions that pure extraction misses. A well-reasoned minority can beat a poorly-reasoned majority.

Tuning invariant: The judge must evaluate reasoning quality, not default to the majority answer. A judge that always picks the most common answer is a more expensive vote.

reasoning-judge-score-pick 6 static · 7 dynamic

3 agentsL1 calls+N aggregationL0 calls · N=3=6 static / 7 dynamic
L0 USED scoring method · workflow aggregation-scoring
3 agents (independent)→ scorer rates each vs rubric

Each response is scored against defined criteria (accuracy, completeness, clarity), producing per-response score profiles rather than just a winner. A unanimous fallback keeps consensus deterministic while scorer jobs remain visible and scheduled.

What makes it unique: The only primitive that produces per-criteria scores. You learn not just which response is best, but why and on which dimensions. Supports dynamic rubrics.

Tuning invariant: Each response scored independently against criteria, not compared to others (that's judge). Collapsing to one "is this right?" dimension makes this a more expensive vote.

reasoning-peer-score-pick 9 static · 10 dynamic

3 agentsL1 calls+N×(N-1) aggregationL0 calls · 6 peer evals=9 static / 10 dynamic
L0 USED peer_matrix method · workflow aggregation-peer-matrix
3 agents (independent)→ each agent's model scores the others→ aggregate scores

Each agent's underlying model evaluates the other agents' responses, routed to the reviewing agent's own model — true evaluator diversity, not just redundancy. Evaluators are blind and do not see their own response.

What makes it unique: The only primitive with multiple evaluator perspectives. The same diverse models that answered also evaluate each other — different models catch different flaws.

Model routing: Each agent's model is propagated via __model keys. Routing is strict: each reviewer must have a model configured. A separate rubric_model controls dynamic rubric generation (required when rubric_mode is dynamic), and dynamic prompts must include {{rubric}}.

Per-criterion scoring: Each peer evaluation returns per-criterion reasoning and scores. The weighted total is computed deterministically from rubric weights — not estimated by the LLM. Fallback parsing supports legacy single-score format.

Tuning invariant: Each agent's model must evaluate independently and must not see its own response. Routing all evaluations through a single model would make this a more expensive scored.

reasoning-informed-captain-synthesis 4 calls total

3 agentsL1 calls+1 aggregationL0 call · synthesis=4 total
L0 USED synthesis method · workflow aggregation-synthesis
3 agents (independent)→ synthesizer generates NEW text

A synthesizer reads all responses and creates a new, unified answer combining the best insights from each. The output is new text, not any agent's original response.

What makes it unique: The only primitive where aggregation creates new content. Every other primitive selects, scores, or counts existing responses. Synthesis merges complementary strengths — one agent's structure with another's insight.

Tuning invariant: The synthesizer must produce new text integrating multiple responses. If the prompt tells it to pick the best/majority answer, it becomes a more expensive judge.

reasoning-adversarial-defense-judge-pick 7 normal · 8 preview

6 agentsL1 calls · 3 R1 + 3 R2+1 top-level judgeL0 call=7 normal(+1 repair in preview)
L0 USED judge method · workflow aggregation-judge
R1: 3 agents (independent)→ R2: 3 agents defend + attack→ judge decides

R1: three models answer independently. R2: each agent sees the others and must defend its own position while challenging the rest — citing specific errors, unsupported claims, logical gaps. A judge evaluates the defenses and picks the winner.

What makes it unique: The only primitive with adversarial pressure after independent answering, and the only one with a genuine multi-round exchange between agents. Unlike deliberation (encourages convergence), debate encourages divergence — surfacing objections convergent discussion would paper over. A defense that withstands challenge signals high confidence. (Don't confuse this with the debate_decide aggregation method below — that one has no live exchange.)

Tuning invariant: R1 must be independent. R2 must be adversarial (defend + challenge). If R2 asks agents to "reconsider," this becomes deliberation. If R2 is removed, it's a more expensive judge.

reasoning-camp-split-judge-pick 4 normal · 5 preview

3 agentsL1 · the debate+1 top-level debate_decideL0 verdict=4 normal(+2 branch jobs in preview)
L0 USED debate_decide method · workflow aggregation-debate-decide
3 agents (independent)→ group by answer into camps→ judge decides between camps

Responses are grouped by extracted answer into "camps." If all agree, the fallback selection makes that agreed answer win deterministically. On disagreement, a judge evaluates the competing positions — seeing each camp's collected reasoning, not individual responses. If no agent yields an extractable answer (e.g. free-form math), aggregation delegates to a synthesis call instead.

The debate lives at L1; the verdict is L0. The three L1 agents generate the competing positions — grouped by answer into opposing camps — and that is the debate. The debate_decide aggregation call renders the verdict over those camps. So the debate is the 3 agent calls (decided in a single pass — agents don't rebut each other across rounds). For a multi-round back-and-forth exchange, see reasoning-adversarial-defense-judge-pick above.

What makes it unique: Combines independent answering with structured disagreement analysis. The judge evaluates positions with supporting arguments rather than individual responses. The unanimous fallback keeps consensus deterministic while the compiled judge job remains visible for faithful DAG preview.

Tuning invariant: Agents answer independently (not knowing about camps). The judge must be able to override the majority camp if the minority's reasoning is stronger — always picking the larger camp is a more expensive vote.

reasoning-multi-round-majority-pick 6 calls total

6 agentsL1 calls · 3 R1 + 3 R2+0 aggregationL0 calls=6 total(tie → synthesis, +1)
L0 USED majority_vote method · workflow aggregation-majority-vote
R1: 3 agents (independent)→ R2: each sees others, revises→ majority_vote

Two rounds. R1: agents answer independently. R2: each agent sees the others' R1 answers and may revise. Final answers come from majority vote on R2 responses.

What makes it unique: The only multi-round primitive. Agents can change their minds after seeing peer reasoning. Holding a position after counterarguments signals high confidence; switching means a flaw was found.

Tuning invariant: R1 independent. R2 must show each agent the others' R1 responses and allow revision. Without peer exposure in R2, this is vote at double cost. Forcing convergence loses the signal from agents that hold position.
